# 전투 타임라인·기록서·공용 소모품 개편 설계

## 목적

서로 다른 여섯 변경을 한 번에 뒤섞지 않고, 공유 데이터와 UI 경계를 기준으로 네 단계로 나누어 순차 구현한다. 각 단계는 설계·구현·검증까지 끝낸 뒤 다음 단계로 넘어가며, 전투 결과를 계산하는 코드와 표시 UI를 분리한다.

## 확정 요구사항

1. 턴 종료 시 캐릭터가 기억 행동을 등록한 타임라인 슬롯 하나당 카르마 0.5를 얻는다.
2. 한 슬롯에 같은 캐릭터의 기억 행동이 여러 개 있어도 해당 슬롯은 한 번만 계산한다.
3. 타임라인 슬롯은 5개이므로 한 캐릭터의 턴당 기본 카르마 획득 상한은 2.5다.
4. 0.5 카르마는 즉시 실제 잔량에 반영하며, 획득 표시와 자원 아이콘에서 절반 회복을 확인할 수 있어야 한다.
5. 월드 몬스터 클릭으로 열리는 몬스터 정보 패널을 제거한다.
6. 타임라인 행동 호버 시 상세 툴팁을 표시한다.
7. 행동 호버 시 해당 행동 소유자 아이콘을 전면·알파 1로 표시하고, 기존 선두 아이콘은 뒤로 보내 대기 알파를 적용한다. 호버 종료 시 실제 행동 순서 표시로 복구한다.
8. 기록서의 재료·효과 탭을 제거하고 몬스터 탭을 추가한다.
9. 연성제를 캐릭터별 장착물이 아닌 탐사 파티 공용 소모품으로 전환한다. 최대 네 개를 장착하고 전투에서 네 슬롯으로 사용한다.
10. 전투 UI의 기존 연성제 버튼과 하단 문구를 제거하고 그 위치로 Z/X Undo·Redo 버튼을 옮긴다. 기존 Undo·Redo 위치에는 소모품 네 슬롯을 2×2로 배치한다.
11. 기억 행동이 취소되거나 실행 시 무효화되면 해당 행동은 카르마 획득 근거에서 제외한다.
12. 공용 소모품은 ID 중복을 허용하는 개별 4개이며, 각 슬롯은 탐사에 가져온 소모품 1개를 나타낸다.
13. 소모품은 행동 예약 단계에서 타임라인에 등록하지 않고 즉시 사용한다.
14. 몬스터는 최초 조우 시 해당 몬스터의 모든 패턴을 기록서에 공개한다.
15. 기록서에서 제거하는 탭은 현재 `Item`과 `Effect`이며 `Fragment`와 `Compound`는 유지한다.

## 목표와 비목표

### 목표

- 여섯 변경을 회귀 원인을 좁힐 수 있는 작은 단계로 구현한다.
- 기존 타임라인 명령, 몬스터 패턴 데이터, 기록서 발견 체계와 연성제 데이터를 가능한 한 재사용한다.
- 카르마와 소모품 사용은 호스트 권위의 `Command -> State Change -> Result/Event` 흐름을 따른다.
- 저장·전달·네트워크 스냅샷은 Scene Object가 아닌 안정적인 ID와 값으로 구성한다.

### 비목표

- 타임라인 슬롯 수와 슬롯당 행동 용량을 변경하지 않는다.
- 타임라인 행동의 실제 실행 순서를 변경하지 않는다.
- 전투 중 별도로 사용하는 몬스터 전투 정보 UI까지 일괄 삭제하지 않는다.
- 이번 작업에서 네트워크 프레임워크를 새로 도입하지 않는다.
- 연성제 효과 자체의 밸런스나 효과 정의를 재설계하지 않는다.

## 제약

- 문서는 `AI_Docs`에만 둔다.
- 테스트는 `Assets/Tests/EditMode~/` 또는 `Assets/Tests/PlayMode~/`에만 둔다.
- Unity batchmode는 사용하지 않는다.
- 고정 UI는 씬 또는 프리팹 배치를 우선한다.
- 전투 결과에 영향을 주는 수치 계산은 UI에서 수행하지 않는다.
- 카르마 반 단위 계산에 `float`를 사용하지 않는다.

## 검토한 접근

### 선택: 기능 경계별 수직 단계

타임라인 표시, 몬스터 정보, 카르마, 공용 소모품을 각각 완결한 뒤 다음 단계로 이동한다. 각 단계가 독립적으로 컴파일·테스트 가능하고 회귀 발생 시 원인을 좁힐 수 있다. 타임라인 호버 두 기능과 몬스터 정보 두 기능처럼 실제 데이터와 이벤트를 공유하는 작업은 같은 단계로 묶는다.

### 제외: 전체 데이터 모델 선행 변경

카르마와 소모품 모델을 먼저 모두 바꾼 뒤 UI를 한꺼번에 연결하면 중간 상태가 오래 유지되고, 저장·전투·네트워크 회귀가 동시에 발생할 가능성이 높다.

### 제외: 화면 우선 임시 연결

UI부터 배치하고 기존 캐릭터별 연성제 상태에 임시로 연결하면 이후 공용 소모품 모델 전환 때 UI와 저장 구조를 다시 뜯어야 한다. UI가 전투 상태를 직접 변경할 위험도 있어 제외한다.

## 1단계: 타임라인 호버 표시

### 현재 구조

- 행동 아이콘 호버는 `TimelineSkillIconHoverUI`가 받는다.
- 상세 팝업 기반은 `TimelineSkillHoverPopupUI`와 `TimelineSkillHoverPopupView`에 이미 있다.
- `BattleTimelineGroupUI`는 한 슬롯의 행동 엔트리와 최대 5개의 소유자 아이콘 큐를 표시한다.
- 기본 상태에서는 실제 행동 순서의 선두 아이콘이 알파 1이고 나머지는 대기 알파를 사용한다.

### 설계

1. `TimelineSkillIconHoverUI`가 호버 진입 시 현재 `BattleTimelinePreviewEntry`를 상세 팝업과 소유자 강조 처리에 함께 전달한다.
2. 상세 툴팁은 행동 이름, 설명, 비용, 행동 종류 및 현재 데이터로 확정 가능한 대상·범위 정보를 표시한다. 표시 문구는 기존 스킬/몬스터 행동 설명 포매터와 로컬라이제이션을 재사용한다.
3. `BattleTimelineGroupUI`는 호버 대상 엔트리의 소유자 아이콘 인덱스를 찾는다.
4. 호버 소유자 아이콘을 형제 순서상 가장 앞으로 올리고 알파를 1로 만든다.
5. 원래 선두를 포함한 나머지 아이콘은 원래 상대 순서를 유지한 채 뒤에 그리고 대기 알파를 적용한다.
6. 호버 종료, 아이콘 비활성화, 슬롯 리바인딩 시 호버 임시 상태를 해제하고 실제 행동 순서 기반 정렬과 알파를 다시 적용한다.
7. 같은 소유자의 연속 행동이 기존 규칙에 따라 하나의 아이콘으로 묶인 경우 그 그룹 아이콘을 강조한다.
8. UI 상태만 변경하며 예약 명령, `OrderIndex`, 실행 배치에는 영향을 주지 않는다.

### 검증 기준

- 플레이어 기억 행동과 몬스터 행동 모두 가능한 상세 데이터가 툴팁에 표시된다.
- 두 번째 이후 소유자 행동을 호버하면 해당 소유자 아이콘만 전면·알파 1이 된다.
- 기존 선두는 뒤로 이동하고 대기 알파가 적용된다.
- 호버 종료 후 원래 순서와 알파가 정확히 복원된다.
- 슬롯 리바인딩·행동 실행·아이콘 제거 도중 임시 호버 상태가 남지 않는다.

## 2단계: 몬스터 정보 경로 통합

### 현재 구조

- 월드 몬스터 클릭 패널은 `MonsterInfoPanelUI`와 Battle 씬의 `MonsterInfoPanel` 계층을 사용한다.
- 전투 HUD에는 별도의 `BattleMonsterInfoPanelUI`가 있다.
- 몬스터 행동·패턴 정보는 `MonsterPatternInfoDatabase`, `MonsterPatternInfoData`, 몬스터 스킬 데이터로 이미 조회 가능하다.
- 기록서는 `RecordPanelUI`가 Skill, Fragment, Relic, Compound, Item, Effect 탭을 관리한다.

### 설계

1. 월드 몬스터 클릭 입력에서 `MonsterInfoPanelUI`를 여는 경로와 그 전용 포커스/블러 연결을 제거한다.
2. 전투 HUD의 `BattleMonsterInfoPanelUI`는 요청 범위가 아니므로 유지한다.
3. 기록서 `Item` 및 `Effect` 탭 버튼·바인딩·콘텐츠 분기를 제거하고 `Monster` 탭을 추가한다. `Fragment`와 `Compound` 탭은 유지한다.
4. 몬스터 탭은 목록과 상세 영역으로 구성한다.
   - 목록: 발견 상태, 몬스터 이름, 대표 이미지
   - 상세: 이름, 이미지, 행동 종류, 행동 순서/패턴, 행동별 설명
5. 몬스터 목록은 안정적인 `MonsterId`를 키로 사용한다.
6. 상세 정보는 기존 몬스터 마스터/스킬/패턴 DB를 조합해 만든다. 새 몬스터 추가를 위해 enum이나 전용 switch를 추가하지 않는다.
7. 발견 여부는 `RecordDiscoveryService`에 `MonsterId` 기반 조우 기록을 추가해 관리한다. 몬스터를 최초 조우하면 해당 몬스터와 그 몬스터의 모든 행동·패턴을 한 번에 공개한다. 미조우 몬스터는 기존 기록서의 잠금 표현을 따른다.
8. 반복 항목은 프리팹화하고, 고정 목록/상세 루트는 기록서 프리팹에 배치한다.

### 검증 기준

- 월드 몬스터 클릭으로 제거 대상 패널이 열리지 않는다.
- 전투 HUD 몬스터 정보는 계속 동작한다.
- 기록서에 재료·효과 탭이 없고 몬스터 탭이 존재한다.
- 발견된 몬스터의 이름·이미지·행동 종류·패턴을 기존 DB와 동일하게 표시한다.
- 몬스터 최초 조우 시 해당 몬스터의 모든 행동·패턴이 공개되고 저장된다.
- 미발견 데이터가 정한 잠금 규칙을 우회해 노출되지 않는다.

## 3단계: 타임라인 등록 기반 카르마

### 자원 표현

- 카르마는 반 단위를 표현하는 정수 고정소수점을 사용한다.
- 내부 카르마 단위 1은 표시값 0.5다.
- 표시 최대 카르마 5는 내부 최대치 10이다.
- 표시 비용 1은 내부 비용 2다.
- 카르마 이외 고유 자원은 기존 정수 단위를 유지한다.
- 저장과 네트워크에는 정수 내부 단위만 기록해 부동소수점 오차를 제거한다.

카르마 단위 변환은 공용 변환 유틸리티/정책 한 곳에 둔다. 기존 `MaxResource`, `CurrentResource`, `ReservedResourceCost`, 스킬 비용, 효과 값의 의미를 호출부마다 임의로 해석하지 않도록 카르마 여부를 확인하는 변환 경계를 제공한다. 이전 저장값은 로드 정규화 단계에서 기존 표시 단위로 보고 내부 단위로 한 번 변환하며, 스키마 버전으로 중복 변환을 방지한다.

### 턴 종료 계산

1. 기존 고정 턴당 1 회복을 제거한다.
2. 각 기억 행동의 실행 결과에는 원래 타임라인 슬롯 인덱스, `CharacterId`, 기억 행동 여부와 카르마 집계 적격 여부를 남긴다. 취소되었거나 실행 시 무효화된 행동은 부적격 결과로 기록한다.
3. 턴 종료 시 호스트가 해당 턴의 확정 실행 결과를 캐릭터별·원래 타임라인 슬롯별로 집계한다.
4. 한 슬롯에 해당 `CharacterId`의 적격 기억 행동 결과가 하나 이상 있으면 점유 슬롯 수를 1 증가시킨다.
5. 같은 슬롯의 중복 행동은 추가 계산하지 않는다.
6. 기본 행동, 이동, 취소된 명령, 무효화된 명령, 몬스터 명령은 기억 등록으로 계산하지 않는다.
7. 획득 내부 단위는 점유 슬롯 수와 같다. 따라서 표시 획득량은 `점유 슬롯 수 × 0.5`, 최대 2.5다.
8. 장비 효과가 기본 카르마 획득을 증감하는 기존 경로가 있다면 내부 단위 변환 후 동일한 결정적 순서로 적용한다.
9. 최대 자원을 초과한 부분은 기존처럼 버린다.
10. 결과는 `CharacterId`, 적격 슬롯 인덱스 집합, 이전 값, 실제 획득 내부 단위, 최종 값을 담은 결과로 UI에 전달한다.
11. 턴 종료 후 집계가 끝나면 해당 턴의 카르마 집계 결과를 정리한다. UI 계층이나 이미 제거된 타임라인 아이콘을 다시 조회하지 않는다.

### 표시

- 획득 피드는 실제 획득량을 `+0.5`, `+1`, `+1.5` 형식으로 표시한다.
- 현재 카르마가 2.5라면 아이콘 2개는 완전 점등하고 세 번째 아이콘은 절반 점등한다.
- 반 점등은 전용 UI 표현으로 처리하며 전투 계산에 관여하지 않는다.
- 예약 미리보기, 설정 패널, 파티 패널과 카르마 툴팁도 같은 표시 변환을 사용한다.

### 검증 기준

- 0~5개의 서로 다른 타임라인 슬롯 점유가 각각 0~2.5 획득으로 계산된다.
- 같은 슬롯의 동일 캐릭터 기억 여러 개는 0.5만 지급한다.
- 여러 캐릭터가 같은 슬롯에 기억을 등록하면 각 캐릭터가 그 슬롯을 독립적으로 1회 계산한다.
- 취소되거나 실행 시 무효화된 기억은 지급 근거에서 제외된다.
- 같은 슬롯에 적격 기억과 무효 기억이 함께 있으면 해당 슬롯은 적격 기억 때문에 한 번만 계산된다.
- 기억이 없는 캐릭터는 카르마를 얻지 않는다.
- 최대치, 예약, 취소, Undo/Redo 이후 값이 반 단위에서 정확하다.
- 저장 및 네트워크 왕복 후 반 카르마가 보존된다.
- 2.5 잔량이 2개 완전 점등과 1개 반 점등으로 표시된다.

## 4단계: 연성제의 공용 소모품 전환

이 단계는 데이터 이전, 탐사 장착, 전투 명령, UI 배치 순으로 내부 검증 지점을 둔다.

### 공용 데이터 모델

1. 연성제는 기존 `CompoundId`와 효과 DB를 재사용하되, 런타임 역할을 소모품으로 정의한다.
2. 탐사 파티 공용 장착 상태에 길이 4의 소모품 슬롯을 둔다.
3. 각 슬롯은 안정적인 `ItemId` 하나만 보유하며 전투 중 한 번 사용할 수 있다. 캐릭터 참조와 UI 참조는 저장하지 않는다.
4. 같은 `ItemId`를 여러 슬롯에 장착할 수 있다. 네 슬롯은 ID 중복 여부와 관계없이 각각 별도의 소모품 한 개로 취급한다.
5. 로비 보관 목록, 탐사 장착 상태, 전투 슬롯별 사용 여부를 분리한다.
6. 기존 캐릭터별 연성제 장착 데이터는 저장 마이그레이션에서 해제하고 공용 보관함으로 돌린다. 동일 ID도 개별 아이템 수량을 잃지 않도록 보존한다.
7. 로비 저장, 탐사 시작 전달, 전투 스냅샷, 멀티플레이 동기화에 공용 4슬롯과 슬롯별 사용 여부를 포함한다.

### 탐사 장착 UI

- 캐릭터별 연성제 장착 영역과 선택 흐름을 제거한다.
- 탐사 준비 영역에 공용 소모품 네 슬롯을 별도 배치한다.
- 보관함에서 슬롯으로 장착·교체·해제할 수 있게 한다.
- 같은 ID의 중복 장착을 허용하되 실제 보유 개수를 초과하지 않도록 공용 검증 서비스에서 판정한다.
- UI는 장착 명령을 요청하고 확정된 공용 장착 상태를 다시 표시한다.

### 전투 사용 흐름

1. 행동 예약 단계에서 슬롯 클릭은 타임라인 명령이 아닌 즉시 사용 `UseConsumableCommand`를 생성한다.
2. 명령은 사용자/파티 식별자, 소모품 슬롯 인덱스, `ItemId`, 필요한 대상 ID를 포함한다.
3. 호스트는 현재 단계가 행동 예약 단계인지, 슬롯 내용, 미사용 상태, 대상 유효성 및 중복 요청을 검증한다.
4. 성공 시 해당 슬롯을 사용 완료로 바꾸고 기존 연성제 효과 서비스를 호출해 상태를 즉시 변경한다.
5. 소모품 사용은 타임라인 예약 이력에 들어가지 않으며 Z/X Undo·Redo 대상이 아니다.
6. 결과 이벤트는 사용된 슬롯, `ItemId`, 사용 완료 상태, 적용 결과를 전달한다.
7. UI/VFX/사운드는 결과 이벤트만 소비한다.

소모품별 대상 지정과 사용 가능 시점은 기존 연성제 효과 정의를 우선 재사용하고, 효과 데이터만으로 판정할 수 없는 경우 DB에 대상/사용 시점 메타데이터를 추가한다. 새 소모품마다 enum·switch·전용 버튼 코드를 추가하는 구조는 피한다.

### 전투 UI

- 기존 연성제 버튼과 하단 텍스트를 제거한다.
- 해당 위치로 Z/X Undo·Redo 버튼을 이동한다.
- 기존 Undo·Redo 영역에 소모품 네 슬롯을 2×2로 배치한다.
- 각 슬롯은 아이콘과 미사용/사용 완료 상태, 사용 가능/불가 상태, 선택/대상 지정 상태를 표시한다. 스택 수량 표시는 사용하지 않는다.
- 고정 루트와 슬롯은 Battle 씬/프리팹에서 명시적 참조로 연결한다.

### 검증 기준

- 캐릭터 전환과 관계없이 동일한 공용 네 슬롯이 표시된다.
- 동일 ID 네 개를 포함해 보유 개수 범위 안에서 임의의 중복 구성을 네 슬롯에 장착할 수 있다.
- 탐사 시작과 네트워크 스냅샷 이후 슬롯 ID·사용 여부가 동일하다.
- 권한 없는 요청, 빈 슬롯, 이미 사용한 슬롯, 예약 단계 외 요청, 잘못된 대상은 상태를 변경하지 않는다.
- 성공한 사용만 해당 슬롯을 정확히 한 번 사용 완료로 바꾼다.
- Undo/Redo 버튼은 이동 후에도 Z/X 단축키와 기존 예약 이력을 유지한다.
- 기존 연성제 버튼·문구와 캐릭터별 장착 UI가 남지 않는다.

## 단계별 산출물과 진행 순서

1. 타임라인 호버 상세/소유자 강조: 코드·프리팹·EditMode 테스트·컴파일 검증
2. 월드 몬스터 패널 제거/기록서 몬스터 탭: 코드·기록서 프리팹 또는 씬·발견 테스트·컴파일 검증
3. 반 단위 카르마/슬롯 점유 계산: 데이터·전투 서비스·네트워크/저장·UI·EditMode 테스트·컴파일 검증
4. 공용 소모품: 저장 마이그레이션·탐사 장착·전투 명령/결과·Battle UI·네트워크 테스트·컴파일 검증

각 단계 완료 보고 후 다음 단계로 넘어간다. 승인된 설계를 실질적으로 바꿔야 할 때만 다시 사용자 결정을 받는다.

## 멀티플레이 영향

- 1·2단계는 로컬 표시와 정보 탐색만 변경하여 전투 결과에 영향이 없다.
- 3단계는 카르마 내부 단위와 턴 종료 상태 변경을 바꾸므로 호스트 계산, 스냅샷, 예약 비용을 함께 갱신해야 한다.
- 4단계는 파티 공용 소모품 장착과 사용 상태가 새 동기화 대상이 된다. 사용은 반드시 호스트 검증 명령과 결과 이벤트를 거쳐야 한다.
