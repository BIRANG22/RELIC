# Steam 로비 파티 권한 동기화 설계

## 목표

Steam 로비의 모든 참가자가 동일한 3인 파티 구성을 보도록 동기화하고, 인원수와 참가 순서에 따라 각 플레이어가 정해진 슬롯만 편집할 수 있게 한다.

이번 단계에서는 다음을 보장한다.

- 호스트만 파티 상태를 확정한다.
- 클라이언트는 자신에게 배정된 슬롯만 변경 요청할 수 있다.
- 슬롯 간 캐릭터 중복을 허용하지 않는다.
- 참가 및 퇴장으로 슬롯이 바뀌더라도 기존 플레이어가 조작하던 캐릭터를 유지한다.
- Steam 로비 밖에서는 기존 싱글플레이 파티 편집 흐름을 유지한다.

## 범위

포함:

- Steam 로비 파티 슬롯 소유권
- 캐릭터 선택 요청과 호스트 검증
- 확정된 파티 스냅샷 동기화
- 참가 및 퇴장에 따른 슬롯 소유권과 캐릭터 재배치
- 권한 없는 슬롯과 중복 캐릭터의 UI 선택 제한
- 호스트 퇴장 시 로비 종료 및 로컬 편집 상태 복귀

제외:

- 전투 상태 동기화
- 전투 입력 및 턴 권한
- 캐릭터 스킬, 룬, 장비 세부 데이터 동기화
- 호스트 마이그레이션
- 별도의 전투용 네트워크 프레임워크 도입

## 권한 모델

호스트를 파티 상태의 유일한 확정 권한으로 둔다. 각 슬롯은 다음 상태를 가진다.

```text
LobbyPartySlotState
- SlotIndex: 0~2
- OwnerSteamId: 슬롯 편집 권한을 가진 플레이어
- CharacterId: 슬롯에 배치된 캐릭터
```

파티 전체 상태는 다음 정보를 추가로 가진다.

```text
LobbyPartySnapshot
- HostSteamId
- Revision
- OrderedClientSteamIds
- Slots[3]
```

`Revision`은 호스트가 확정 상태를 변경할 때마다 증가한다. 클라이언트는 현재 적용한 값보다 높은 Revision만 적용한다.

슬롯 소유권은 인원수에 따라 아래처럼 고정한다.

| 인원 | 1번 슬롯 | 2번 슬롯 | 3번 슬롯 |
|---|---|---|---|
| 1명 | 호스트 | 호스트 | 호스트 |
| 2명 | 호스트 | 호스트 | 클라1 |
| 3명 | 호스트 | 클라1 | 클라2 |

여기서 클라1과 클라2는 호스트가 기록한 참가 순서에 따른다. Steam이 반환하는 현재 멤버 배열 순서는 권한 순서의 근거로 사용하지 않는다.

## 참가 및 퇴장 규칙

### 1명에서 2명

```text
변경 전: [호스트:A] [호스트:B] [호스트:C]
변경 후: [호스트:A] [호스트:B] [클라1:C]
```

3번 슬롯의 캐릭터는 유지하고 소유권만 클라1에게 이전한다.

### 2명에서 3명

```text
변경 전: [호스트:A] [호스트:B] [클라1:C]
변경 후: [호스트:A] [클라1:C] [클라2:B]
```

2번과 3번 캐릭터를 교환한다. 클라1은 기존에 조작하던 캐릭터를 유지하며 2번 슬롯으로 이동하고, 새로 들어온 클라2는 3번 슬롯을 받는다.

### 3명 상태에서 클라1 퇴장

```text
변경 전: [호스트:A] [클라1:C] [클라2:B]
변경 후: [호스트:A] [호스트:C] [클라2:B]
```

캐릭터 이동 없이 2번 슬롯 소유권만 호스트에게 반환한다.

### 3명 상태에서 클라2 퇴장

```text
변경 전: [호스트:A] [클라1:C] [클라2:B]
변경 후: [호스트:A] [호스트:B] [클라1:C]
```

2번과 3번 캐릭터를 교환한다. 클라1은 기존 캐릭터를 유지하면서 3번 슬롯으로 이동한다.

### 2명 상태에서 클라1 퇴장

```text
변경 전: [호스트:A] [호스트:B] [클라1:C]
변경 후: [호스트:A] [호스트:B] [호스트:C]
```

캐릭터는 유지하고 3번 슬롯 소유권만 호스트에게 반환한다.

같은 멤버 구성에 대한 Steam 콜백이 반복되어도 재배치가 다시 실행되지 않아야 한다. 호스트는 이전 멤버 집합과 참가 순서를 비교하여 실제 구성 변경이 있을 때만 새 상태를 확정한다.

## 캐릭터 변경 명령

UI는 Steam 로비에 참가한 동안 `PartyRuntimeStore`를 직접 변경하지 않는다. 다음 명령을 생성한다.

```text
LobbyPartyCharacterChangeCommand
- RequesterSteamId
- SlotIndex
- RequestedCharacterId
- KnownRevision
- RequestId
```

클라이언트는 Steam 로비 채팅 메시지로 명령을 호스트에게 보낸다. 호스트 자신의 선택도 동일한 검증 함수를 사용하지만 네트워크 왕복 없이 처리한다.

호스트는 다음 조건을 모두 만족할 때만 명령을 승인한다.

1. 요청자가 현재 로비 멤버다.
2. 요청자가 대상 슬롯의 현재 소유자다.
3. 요청의 KnownRevision이 호스트의 현재 Revision과 같다.
4. 캐릭터 ID가 비어 있지 않고 로컬 캐릭터 데이터베이스에 존재한다.
5. 요청한 캐릭터가 다른 슬롯에서 사용 중이지 않다.

승인 시 호스트는 캐릭터를 변경하고 Revision을 증가시킨 후 전체 파티 스냅샷을 발행한다. 거부 시 파티 상태를 변경하지 않는다. 클라이언트 UI는 마지막 확정 스냅샷 상태를 계속 표시한다.

## 스냅샷 발행과 적용

호스트는 세 슬롯을 하나의 직렬화된 스냅샷으로 만들어 Steam 로비 데이터에 기록한다. 슬롯별 키를 순차적으로 기록하지 않아 중간 상태가 노출되지 않게 한다.

클라이언트는 로비 데이터 변경 콜백을 받으면 다음 순서로 검증한다.

1. 현재 Steam 로비 소유자가 스냅샷의 HostSteamId와 같은지 확인한다.
2. 스냅샷 Revision이 현재 적용된 Revision보다 높은지 확인한다.
3. 슬롯 수와 슬롯 인덱스가 올바른지 확인한다.
4. 슬롯 소유자가 현재 로비 멤버인지 확인한다.
5. 비어 있지 않은 CharacterId가 서로 중복되지 않는지 확인한다.
6. 유효하면 세 슬롯을 한 번에 로컬 상태에 적용한다.

적용 후 `PartyRuntimeStore`와 파티 슬롯 UI, 캐릭터 버튼 사용 가능 상태를 갱신한다.

초기 참가자는 로컬에 남아 있는 파티 구성을 먼저 확정 상태로 간주하지 않는다. 호스트가 발행한 최초 스냅샷을 받아 적용해야 동기화 완료 상태가 된다.

## 구성 요소

### `LobbyPartyAuthorityState`

Unity UI와 Steam API를 참조하지 않는 순수 C# 상태 객체다.

- 슬롯 소유권과 캐릭터 저장
- 참가 순서 저장
- 참가 및 퇴장 재배치
- 캐릭터 변경 명령 검증
- Revision 증가
- 확정 스냅샷 생성

### `LobbyPartyCommand`

클라이언트가 호스트에게 보내는 변경 요청 데이터와 직렬화 규칙을 담당한다.

### `LobbyPartySnapshot`

호스트가 확정한 전체 파티 상태와 직렬화 규칙을 담당한다.

### `SteamLobbyPartySynchronizer`

Steam과 순수 파티 상태 사이의 어댑터다.

- 현재 로비와 호스트 식별
- 로비 채팅 메시지 송수신
- 멤버 참가 및 퇴장 감지
- 호스트의 스냅샷 발행
- 클라이언트의 스냅샷 검증 및 적용
- 호스트 퇴장 처리

### `SteamLobbyInviteController`

기존 책임인 Steam 초기화, 로비 생성과 참가, 초대 및 상태 표시를 유지한다. 파티 동기화 자체는 `SteamLobbyPartySynchronizer`에 위임한다.

### 캐릭터 선택 UI

- 로컬 플레이어가 소유한 슬롯만 선택 가능하게 한다.
- 다른 플레이어가 소유한 슬롯 클릭은 상태를 바꾸지 않는다.
- 다른 슬롯에서 사용 중인 캐릭터 버튼은 선택 불가 상태로 표시한다.
- 콜백 지연 중 발생한 중복 요청도 호스트 검증에서 최종 거부한다.
- Steam 로비 밖에서는 기존 로컬 편집 방식을 유지한다.

## 기존 런타임 데이터와의 경계

`PartyRuntimeStore`는 전투, 저장 및 싱글플레이 코드에서도 사용하므로 Steam ID나 네트워크 권한을 저장하지 않는다. 확정된 캐릭터 구성만 보관한다.

파티 동기화 계층의 흐름은 다음과 같다.

```text
UI Command
-> Host Validation
-> Authority State Change
-> Result Snapshot
-> PartyRuntimeStore Apply
-> UI Refresh
```

이 구조는 UI가 직접 파티 결과를 결정하지 않게 하며, 추후 전투 멀티플레이를 추가할 때도 Steam 로비 권한 로직이 전투 핵심 상태에 섞이지 않게 한다.

## 오류 및 연결 종료 처리

- 유효하지 않은 명령은 상태 변경 없이 거부하고 진단 로그를 남긴다.
- 오래된 Revision 요청은 거부한다.
- 오래되거나 손상된 스냅샷은 적용하지 않는다.
- 요청 전송에 실패하면 로컬 화면을 선반영하지 않고 마지막 확정 상태를 유지한다.
- 호스트가 퇴장하거나 연결이 끊기면 클라이언트는 네트워크 스냅샷 적용을 중단하고 Steam 로비를 나간다.
- 호스트 종료 시 마지막으로 적용한 캐릭터 구성은 `PartyRuntimeStore`에 유지한다.
- 로비 종료 후 모든 슬롯을 로컬 플레이어가 편집할 수 있는 싱글 상태로 복귀시킨다.
- 이번 범위에서는 새 호스트 선출이나 파티 유지 기능을 제공하지 않는다.

## 검증 계획

테스트 파일은 빌드 대상에 포함되지 않는 `Assets/Tests/EditMode~/` 아래에만 작성한다. Unity 에디터가 열려 있다고 가정하므로 batchmode 테스트는 실행하지 않는다.

순수 상태 로직 테스트:

- 1명일 때 세 슬롯 모두 호스트 소유
- 2명일 때 호스트, 호스트, 클라1 배치
- 3명일 때 호스트, 클라1, 클라2 배치
- 두 번째 플레이어 참가 시 기존 3번 캐릭터 유지
- 세 번째 플레이어 참가 시 2·3번 교환과 클라1 캐릭터 유지
- 클라1 퇴장 시 2번만 호스트에게 반환
- 클라2 퇴장 시 2·3번 교환과 클라1 캐릭터 유지
- 2명 상태의 클라1 퇴장 시 3번만 호스트에게 반환
- 권한 없는 슬롯 변경 요청 거부
- 이미 사용 중인 캐릭터 요청 거부
- 오래된 Revision 요청 거부
- 반복된 멤버 콜백에도 재교환이 발생하지 않음
- 호스트 종료 시 로컬 편집 상태 복귀

정적 및 컴파일 검증:

- Unity가 생성한 C# 프로젝트를 MSBuild로 컴파일한다.
- Steamworks.NET API 사용부가 현재 설치 버전과 일치하는지 확인한다.

수동 멀티플레이 검증:

- Steam 계정 2개와 3개 구성에서 각각 참가 및 퇴장 규칙 확인
- 권한 없는 슬롯 클릭이 양쪽 화면에 영향을 주지 않는지 확인
- 동시에 같은 캐릭터를 선택했을 때 하나의 요청만 승인되는지 확인
- 참가 직후 모든 참가자가 같은 캐릭터와 소유권을 표시하는지 확인
- 호스트 종료 시 클라이언트가 로비를 종료하고 로컬 편집 상태로 돌아오는지 확인

## 완료 조건

- 모든 참가자가 동일한 슬롯 캐릭터와 소유자를 표시한다.
- 각 플레이어는 자신이 소유한 슬롯만 변경할 수 있다.
- 어떤 타이밍에도 확정 파티에 중복 캐릭터가 존재하지 않는다.
- 참가 및 퇴장 후 기존 플레이어의 캐릭터가 규칙에 맞게 유지된다.
- 호스트 종료 후 클라이언트가 잘못된 네트워크 상태에 머물지 않는다.
- 기존 싱글플레이 파티 편집과 전투 데이터 사용 흐름이 유지된다.
