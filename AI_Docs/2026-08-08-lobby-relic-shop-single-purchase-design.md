# 로비 유물 상점 1회 구매 제한 설계

## 목표

로비 유물 상점에서 유물 하나를 구매하면 같은 로비 런타임 동안 나머지 상품 구매와 리롤을 모두 차단한다. 잔액 부족 등 실패한 구매는 제한을 소모하지 않는다.

## 상태 판정

별도 플래그를 저장하지 않는다. `LobbyRuntimeData.RelicOfferIds` 중 하나가 `OwnedRelicIds`에 포함되어 있으면 현재 상점 오퍼에서 이미 구매한 것으로 판정한다. 오퍼 생성 시 기존 보유 유물은 제외되므로 두 목록의 교집합은 상점 구매 성공 후에만 생긴다는 현재 불변식을 사용한다.

공통 정책 `LobbyRelicShopPurchaseLimit.HasPurchasedOffer(runtime)`을 두 서비스와 Presenter가 함께 사용한다.

## 데이터 흐름

1. UI가 유물 ID로 구매 Command를 보낸다.
2. 구매 서비스가 요청, DB, 구매 제한, 중복, 가격, 잔액을 검증한다.
3. 성공한 경우에만 재화를 차감하고 유물을 추가한다.
4. Presenter가 결과를 받아 모든 상품 버튼과 리롤 버튼을 잠그고 호스트 스냅샷을 발행한다.
5. 이후 구매·리롤 Command는 서비스 계층에서도 거부되어 상태를 변경하지 않는다.

## UI 동작

- 구매 전: 기존 규칙대로 상품 및 리롤을 사용할 수 있다.
- 첫 구매 후: 구매한 슬롯은 Sold 표시, 나머지 슬롯은 비활성화한다.
- 상점을 다시 열거나 공유 상태를 다시 그려도 구매 제한 판정으로 잠금이 유지된다.
- 클라이언트는 기존 호스트 전용 변경 규칙을 그대로 따른다.

## 실패 처리

- 두 번째 구매는 `PurchaseLimitReached` 결과를 반환한다.
- 구매 후 리롤은 `PurchaseLimitReached` 결과를 반환한다.
- 실패 시 BlueDustium, 보유 유물, 오퍼, 시드, 리롤 횟수는 변경하지 않는다.

## 검증

- 첫 구매 성공과 두 번째 구매 상태 불변을 EditMode 테스트로 검증한다.
- 구매 후 리롤 상태 불변을 검증한다.
- 구매 실패가 제한을 소모하지 않는지 검증한다.
- Presenter가 구매 상태에서 모든 버튼과 리롤을 비활성화하는 경계를 검증한다.

## 멀티플레이 영향

새 동기화 필드를 추가하지 않는다. 이미 공유되는 `RelicOfferIds`와 `OwnedRelicIds`에서 제한 상태를 결정하므로 호스트 스냅샷 수신 후 모든 참가자가 같은 잠금 상태를 계산한다.
