# 플레이어 예약 Undo/Redo 복구 설계

## 조사 결과

- 예약 추가와 드래그 이동은 `playerReservationHistory`에 각각 `Add`, `Move` 작업으로 기록된다.
- 직접 취소는 실행된 플레이어 작업인데도 Undo 스택이 아니라 Redo 스택에 삭제된 명령을 넣고 있었다.
- 직접 취소 과정의 `RemoveCommandFromNetwork`는 해당 명령과 관련된 기존 Undo 기록을 모두 제거한다.
- 이 조합 때문에 취소가 새로운 작업 단위로 남지 않고, 이전 Undo/Redo 연속성도 깨진다.
- 네트워크 스냅샷 적용은 전체 예약을 비운 뒤 재구성하므로 클라이언트의 로컬 작업 이력을 지운다. 스냅샷만으로는 `Move`와 `Delete` 작업의 전후 위치를 복원할 수 없다.

## 권장 설계

1. 히스토리 작업을 `Add`, `Move`, `Delete`로 명시한다.
2. 직접 취소 성공 시 `Delete`를 Undo 스택에 추가하고, 새로운 플레이어 작업이므로 Redo 스택은 비운다.
3. `Delete` Undo는 원래 슬롯/순서에 명령을 삽입하고, `Delete` Redo는 같은 명령을 다시 제거한다.
4. Undo/Redo 내부 적용 중에는 일반 추가·삭제 기록 로직을 통하지 않아 스택을 재작성하지 않는다.
5. 여러 추가, 이동, 삭제는 각각 독립된 스택 항목으로 유지한다.
6. 네트워크 전투의 Undo/Redo는 게스트가 로컬 상태를 직접 변경하지 않고 호스트 Command로 요청한다.
7. 호스트는 다음 히스토리 항목의 캐릭터 소유권을 검증하고 실행 결과를 Snapshot으로 배포한다.
8. Snapshot에는 다음 Undo/Redo 항목의 캐릭터 ID를 포함해 각 클라이언트 버튼 상태를 호스트 기준으로 계산한다.
9. 다른 플레이어가 열람하거나 예약한 슬롯이라는 이유로 슬롯 전체를 잠그는 제한은 제거한다. 개별 캐릭터 조작 권한 검증은 유지한다.
10. 예약 명령마다 `ReservationId`를 부여하고 Command/Snapshot에 전달한다. 스냅샷 재구성 후 Add/Move/Delete 히스토리의 명령 참조를 이 ID로 다시 연결한다.

## 범위 결정

로컬 Add/Move/Delete 히스토리와 네트워크 호스트 권위형 Undo/Redo를 함께 수정한다. Snapshot으로 이동 이력을 추측하지 않고 호스트가 보유한 실제 작업 스택을 사용한다.

## 멀티플레이 영향

전투 결과 계산은 변경하지 않는다. Undo/Redo를 `Network Command -> Host State Change -> Snapshot` 흐름으로 처리해 멀티플레이 경계를 유지한다.
