# 로비 유물 상점과 로비 인벤토리 설계

## 목표

로비의 Position 상태에서 서로 다른 액티브 유물 3개를 BlueDustium으로 구매하고, 로비 전용 인벤토리에서 장착한 결과를 배틀 시작 시 배틀 런타임으로 전달한다.

## 범위

- `BlueDustium`이라는 로비 전용 재화를 추가한다.
- 저장 데이터가 없는 새 게임에서만 BlueDustium 기본값을 999로 초기화한다.
- BlueDustium 잔액, 로비 보유 유물·스킬·가방 아이템, 로비 장착 상태를 영구 저장한다.
- 로비 Canvas에 Position 상태 전용 `PositionPanel`을 추가한다.
- 월드의 `Position/LightBase/StartRelicSpawnRoot`와 그 자식 3개는 UI 배치 기준점으로 유지한다.
- 보유하지 않은 액티브 유물 중 서로 다른 최대 3개를 진열한다.
- 로비에 배틀씬 `InventoryPanel`과 같은 배치의 로비 전용 패널을 새로 구성하고 로비 런타임 데이터로 연결한다.
- 별도 `BagPanel` UI는 이번 범위에 포함하지 않는다.
- 배틀 시작 직전에 로비의 전투용 보유 및 장착 데이터를 배틀 런타임으로 복사한다.
- BlueDustium은 배틀 런타임으로 복사하지 않는다.

## 데이터 경계

### LobbyRuntimeData

`LobbyRuntimeData`는 배틀 런타임과 분리된 영구 로비 데이터다.

- `BlueDustium`: 현재 로비 재화. 최초 기본값 999.
- `OwnedRelicIds`: 로비에서 보유한 유물 ID 목록.
- `SkillInventoryIds`: 로비에서 보유한 교체 가능 스킬 ID 목록.
- `BagItemIds`: 이후 로비 인벤토리 확장을 위한 가방 아이템 ID 목록.
- 캐릭터별 장착 유물 및 장착 스킬 정보는 안정적인 `CharacterId`와 데이터 ID로 저장한다.

씬 오브젝트 참조는 저장 데이터에 포함하지 않는다. 저장 파일에 로비 데이터가 없을 때만 새 기본 데이터를 생성하며, 불러온 잔액이 0이어도 999로 재설정하지 않는다.

### BattleRuntimeData 전달

배틀 시작 요청은 다음 순서로 처리한다.

1. 로비 파티와 장착 상태를 검증한다.
2. 현재 로비 보유 유물과 스킬 목록의 복사본을 배틀 런타임에 기록한다.
3. 캐릭터별 장착 유물·스킬을 캐릭터 런타임의 배틀 시작 상태에 반영한다.
4. 액티브 유물 사용 횟수 등 배틀 전용 상태를 기존 초기화 흐름으로 생성한다.
5. 배틀씬을 시작한다.

전달 이후 배틀 중 획득·소모·장착 변경은 기존 배틀 런타임에서만 관리하며 로비 영구 데이터에 역으로 자동 반영하지 않는다.

## PositionPanel과 유물 진열

로비 Canvas 아래에 `PositionPanel`을 만들고 `LobbyViewStateController`의 Position 상태에 연결한다. 패널은 로비·캐릭터 선택 상태에서는 비활성화한다.

`StartRelicSpawnRoot`의 자식 3개는 월드 앵커로 사용한다. 각 UI 구매 버튼은 매 프레임 해당 앵커의 월드 좌표를 메인 카메라의 화면 좌표로 변환하고, Canvas 로컬 좌표로 변환해 따라간다. 따라서 거점 카메라를 드래그해도 버튼이 정해진 월드 위치에 붙어 보인다.

각 버튼은 다음 요소를 가진다.

- 유물 아이콘
- BlueDustium 가격 텍스트 및 아이콘
- 구매 가능한 상태의 Button
- 구매 완료 또는 빈 후보 상태 표현

## 후보 선택과 가격

후보는 `RelicDatabase.GetAll()`에서 액티브 유물만 필터링한다. `ActiveRelicEffectResolver.IsActiveRelic`의 기존 판정을 재사용한다.

다음 ID는 후보에서 제외한다.

- `LobbyRuntimeData.OwnedRelicIds`에 이미 존재하는 유물
- 현재 진열 결과에 이미 포함된 유물
- ID나 레어도 데이터가 유효하지 않은 유물

선택은 결과 기록이 가능한 랜덤 인터페이스를 통해 수행한다. 후보가 3개보다 적으면 가능한 수만 진열하고 나머지는 빈 슬롯로 표시한다.

레어도별 고정 가격은 다음과 같다.

| 레어도 | 가격 |
| --- | ---: |
| Common | 100 |
| Uncommon | 200 |
| Rare | 300 |
| Unique | 500 |

## 구매 흐름

구매는 UI가 데이터를 직접 변경하지 않고 구매 Command를 서비스에 전달한다.

1. UI가 선택된 유물 ID로 구매를 요청한다.
2. 서비스가 유물 존재, 액티브 타입, 미보유 상태, 가격, 잔액을 검증한다.
3. 검증 성공 시 BlueDustium을 차감하고 `OwnedRelicIds`에 유물 ID를 추가한다.
4. 변경된 로비 런타임을 저장한다.
5. 구매 결과 이벤트로 재화 HUD, 유물 버튼, 인벤토리를 갱신한다.

실패 시 데이터는 변경하지 않고 실패 사유를 결과로 반환한다. 구매된 버튼은 판매 완료 상태로 비활성화하며 즉시 재추첨하지 않는다.

## 로비 InventoryPanel

배틀씬의 `InventoryPanel` RectTransform, 이미지, 색상과 버튼 배치를 기준으로 로비 전용 패널을 새로 구성한다. Battle씬의 씬 오브젝트 참조는 복사하지 않는다.

캐릭터별 `Skill_List`는 패시브 1칸, 고유 1칸, 전용 1칸, 공유 2칸의 총 5칸이다. 기본 장착 상태에서는 공유 스킬이 1개이므로 아이콘 4개와 빈 공유 스킬 슬롯 1개가 표시된다.

`RelicInventory`에서 유물을 선택한 뒤 캐릭터의 `Relic_List` 슬롯을 클릭하면 장착한다. 장착된 슬롯을 클릭하면 유물을 해제해 인벤토리로 돌려보낸다.

패널 내부 로직이 `DataManager.Instance.BattleRuntimeStore`를 직접 읽는 부분에는 인벤토리 데이터 공급 경계를 둔다.

- 로비 공급자: `LobbyRuntimeData`의 보유 및 장착 데이터를 읽고 변경한다.
- 배틀 공급자: 기존 `BattleRuntimeData`와 캐릭터 런타임을 사용한다.

씬별 공급자가 명시적으로 연결되며, UI는 어느 런타임이 사용되는지 판단하지 않는다. 배틀 중 편집 잠금 규칙은 배틀 공급자에서 유지하고 로비에서는 장착 편집을 허용한다.

## BlueDustium HUD

로비 Canvas에 배틀씬 재화 HUD와 같은 역할과 배치 규칙을 갖는 BlueDustium HUD를 추가한다. 제공된 참고 이미지처럼 아이콘과 숫자를 한 그룹으로 표시하며, 현재 BlueDustium 값을 저장된 로비 데이터에서 읽는다. 구매 성공 이벤트를 받으면 즉시 숫자를 갱신한다.

아이콘 에셋이 프로젝트에 이미 있으면 그것을 사용하고, 없다면 사용자가 지정할 수 있도록 직렬화된 Sprite 슬롯과 명확한 임시 표시를 둔다. 요청 범위 밖의 신규 원본 아트는 생성하지 않는다.

## 오류 처리

- DataManager 또는 로비 저장소가 준비되지 않으면 구매 버튼을 비활성화하고 경고를 남긴다.
- 유물 데이터나 아이콘이 없으면 해당 후보를 빈 슬롯 처리한다.
- 알 수 없는 레어도는 구매 불가로 처리한다.
- 잔액 부족, 중복 구매, 이미 판매된 슬롯 요청은 데이터 변경 없이 실패 결과를 반환한다.
- 저장 실패 시 구매 데이터 변경을 확정하지 않고 실패 결과를 표시한다.

## 테스트

테스트는 빌드 대상에서 제외되는 `Assets/Tests/EditMode~/` 아래에만 작성한다.

- 저장 데이터가 없을 때 BlueDustium이 999로 한 번만 초기화되는지 검증한다.
- 저장된 0 또는 다른 잔액을 불러올 때 999로 덮어쓰지 않는지 검증한다.
- 레어도별 가격이 100, 200, 300, 500인지 검증한다.
- 액티브 유물만 선택되고 보유 유물과 중복 후보가 제외되는지 검증한다.
- 후보 부족 시 남은 슬롯이 비어 있는지 검증한다.
- 구매 성공 시 정확한 금액 차감, 유물 추가, 성공 결과가 발생하는지 검증한다.
- 잔액 부족과 중복 구매 시 데이터가 바뀌지 않는지 검증한다.
- 배틀 시작 전달 시 목록이 복사되고 BlueDustium은 전달되지 않는지 검증한다.
- 로비·캐릭터 선택·Position 상태에 따라 `PositionPanel`이 정확히 비활성화/활성화되는지 검증한다.

Unity 에디터가 항상 열려 있다고 가정하므로, 에디터와 충돌하는 batchmode 테스트는 실행하지 않는다. 가능한 정적 검증과 C# 프로젝트 빌드를 함께 수행한다.

## 제외 사항

- BlueDustium 수급처
- 상점 새로고침 또는 재추첨
- 구매 취소와 환불
- 별도 BagPanel UI의 로비 복제
- 배틀 결과를 로비 영구 인벤토리에 자동 합산하는 기능
- 네트워크 패키지 또는 서버 권한 구조
